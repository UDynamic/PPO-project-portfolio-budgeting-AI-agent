# Test Problem Formulation: PPO for Project Portfolio Budgeting

## 1) Scope and Objective
This document defines a clean and complete formulation of the **Project Portfolio Budgeting** problem as a **reinforcement learning environment** for training a **PPO agent**.

The decision-maker (agent) allocates limited budget across multiple concurrent projects over a finite horizon. Each project has contractual cost/revenue structure, schedule dynamics, payment uncertainty, and performance uncertainty. The goal is to maximize risk-adjusted financial performance while maintaining project execution quality.

---

## 2) Decision Context

### 2.1 Why RL (PPO)?
Portfolio budgeting is sequential and uncertain:
- Decisions at period `t` affect future liquidity, progress, and penalties.
- Outcomes are stochastic (payment delays, inflation, execution variation).
- Trade-offs are multi-objective (profitability, liquidity, completion, risk).

PPO is suitable because it supports:
- Continuous or bounded action spaces.
- Stable policy updates under stochastic transitions.
- Long-horizon optimization with discounted rewards.

### 2.2 Episode Semantics
- One episode = one full portfolio lifecycle across `PD` periods (typically 12).
- At each period, the agent receives a state summary and outputs budget allocation actions.
- Environment simulates project evolution, cash in/out, uncertainties, and constraints.

---

## 3) Sets, Indices, and Horizon
- `i ∈ {1, …, N}`: project index.
- `t ∈ {0, …, PD}`: portfolio period index.
- `N`: number of projects in current portfolio.
- `PD`: portfolio duration (total decision periods).

Project-level duration may vary:
- `d_i ≤ PD`: duration of project `i`.

---


## 4) Project Parameterization
The following structure consolidates your `problemFormulation.md` and notebook logic.

### 4.1 Core Contract and Schedule Variables
For each project `i`:
- `BAC_i`: budget at completion (total planned cost).
- `ROI_i`: return-on-investment margin parameter.
- `TPAC_i = (1 + ROI_i) * BAC_i`: total contractual inflow at completion.
- `d_i`: project duration.
- `dd_{i,t}`: project data date at period `t` (current reporting step).

### 4.2 Cost Baseline (S-curve)
- `L_SC_{i,t}`: cumulative planned cost (S-curve), with:
  - `L_SC_{i,0} = 0`
  - `L_SC_{i,d_i} = BAC_i`
- `PL_SC_{i,t} = L_SC_{i,t} - L_SC_{i,t-1}`: periodic planned cost.
- `Σ_t PL_SC_{i,t} = BAC_i`.

### 4.3 Inflow Curve (Contractual Payment Model)
- `L_IC_{i,t}`: cumulative inflow (expected payment receipts).
- `PL_IC_{i,t} = L_IC_{i,t} - L_IC_{i,t-1}`: periodic inflow.

Payment schedule is generated by one inflow model (as in notebook):
- Milestone-heavy,
- Balanced,
- Back-loaded / completion-heavy.

Advanced and final payments:
- `AP_i`: advance payment share.
- `FP_i`: final payment share.
- Must satisfy contract consistency with `TPAC_i`.

### 4.4 Physical Progress Variables
- `PP_{i,t}`: cumulative project progress in `[0,1]`.
- `L_PP_{i,t}`: cumulative progress trajectory.
- `PL_PP_{i,t} = L_PP_{i,t} - L_PP_{i,t-1}` periodic progress increment.

Completion condition (ideal):
- `L_PP_{i,d_i} = 1`.

### 4.5 EVM-Compatible Metrics
- `BCWS_{i,t}`: budgeted cost of work scheduled (planned value).
- `ACWP_{i,t}`: actual cost of work performed.
- `BCWP_{i,t}`: budgeted cost of work performed (earned value).

Useful derived diagnostics:
- `SV_{i,t} = BCWP_{i,t} - BCWS_{i,t}` (schedule variance),
- `CV_{i,t} = BCWP_{i,t} - ACWP_{i,t}` (cost variance),
- `SPI_{i,t} = BCWP_{i,t} / BCWS_{i,t}` (if denominator > 0),
- `CPI_{i,t} = BCWP_{i,t} / ACWP_{i,t}` (if denominator > 0).

---

## 5) Portfolio-Level Variables
- `NBAC_i = BAC_i / Σ_j BAC_j`: normalized BAC weights.
- `PDD_t`: portfolio data date (current period).
- `B_t`: total available budget to allocate at period `t`.
- `x_{i,t}`: allocated budget/action for project `i` at period `t`.

Budget conservation:
- `x_{i,t} ≥ 0`,
- `Σ_i x_{i,t} ≤ B_t`.

Optional minimum-feasibility rule:
- `x_{i,t} ≥ x_min` for active projects (or encoded as soft penalty).

## 7) MDP Formulation

### 7.1 State Space `s_t`
State should include project-level and portfolio-level summary features:
- Remaining budget and liquidity indicators.
- For each project: 
  - normalized BAC,
  - current progress,
  - remaining duration,
  - expected vs actual payment status,
  - EVM indicators (or compressed forms),
  - delay/risk flags.
- Global macro features (scenario risk, inflation bucket).

Practical implementation uses a flattened numeric vector for Gymnasium `Box` observation space.

### 7.2 Action Space `a_t`
Two practical choices:
1. **Continuous vector allocation**: agent outputs raw scores `u_i`, mapped to feasible `x_{i,t}` by simplex-style normalization.
2. **Discrete allocation policy**: choose among predefined budget split templates.

Given PPO and your notebook direction, continuous allocation is the natural default.

### 7.3 Transition `P(s_{t+1}|s_t,a_t)`
Transition combines deterministic accounting + stochastic shocks:
- Apply allocation `x_{i,t}`.
- Update progress based on funded work and execution uncertainty.
- Update costs (`ACWP`) and planned/earned values.
- Update expected/actual receipts under delay model.
- Update portfolio liquidity and remaining budget.
- Advance time `t → t+1`.

### 7.4 Reward `r_t`
Reward should be multi-term and normalized:

`r_t = w1 * cash_health_t + w2 * progress_quality_t + w3 * value_creation_t - w4 * risk_penalty_t - w5 * infeasibility_penalty_t`

Where examples are:
- `cash_health_t`: positive for maintaining liquidity and reducing negative cash gaps.
- `progress_quality_t`: positive for on-schedule progress.
- `value_creation_t`: positive for earned value/profitability signals.
- `risk_penalty_t`: penalties for delays, volatility exposure, large SPI/CPI deterioration.
- `infeasibility_penalty_t`: hard/soft penalties for breaking budget or starvation rules.

Terminal reward at `t = PD` should emphasize:
- Completion ratio across projects,
- Final cash/profit position,
- Aggregate schedule/cost adherence.

### 7.5 Discount and Horizon
- Finite horizon: `T = PD`.
- Discount `γ` chosen in `[0.95, 0.999]` depending on long-horizon sensitivity.

## 8) Constraints and Feasibility Layer

### 8.1 Hard Constraints
- Nonnegative allocations.
- Portfolio budget cap each period.
- No allocation to completed projects (or automatically clipped to 0).

### 8.2 Soft Constraints (Reward Penalties)
- Underfunding active critical projects.
- Excessive concentration risk in one project.
- Persistent liquidity deficits.

A projection/clipping layer should enforce hard feasibility before state transition.

---

## 12) Research Assumptions (Explicit)
1. Portfolio duration is discretized (e.g., monthly periods).
2. Project planning baselines are known at contract start (`BAC`, baseline schedule).
3. Real-world uncertainty is approximated through calibrated stochastic processes.
4. Agent observes sufficient state statistics (possibly partial but informative).
5. Objective is policy quality under uncertainty, not exact replication of one company’s private ledger.

---

## 13) Final Problem Statement
Given a portfolio of `N` projects over `PD` periods, with project-specific cost baselines, contractual inflows, stochastic delays, and execution uncertainty, determine a policy `π(a_t|s_t)` that allocates budget each period to maximize expected discounted cumulative reward while satisfying budget feasibility and improving final portfolio outcomes (completion, liquidity, and risk-adjusted value creation).
